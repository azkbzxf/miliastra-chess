### 块 1 第一轮：启动崩溃（已修）

```
mountError: OnStart: sim/levelScript.lua:3348: attempt to index a nil value (global 'GAME')
```

| 项 | 内容 |
|---|---|
| 根因 | `show_start_screen()` 定义在 3347 行，函数体第一句 `GAME.screen = "start"` 使用 `GAME`；而 `local GAME = {` 在 **3388 行**，晚于它。Lua 编译期把该 `GAME` 解析为 **global**，运行时为 nil |
| 为什么门禁没抓到 | `lua_check.cjs` 的「局部函数无先用后定义」只查**函数名**的前向引用，**不查函数体内引用的变量声明位置** —— 这是它的盲区 |
| 修法 | 把 `local GAME` 整块（51 行）从第 7 区上移到第 6 区 UI 之前（现 2160 行）；未使用 `GAME = {}` 那种易误解写法 |
| 补充防护 | 新增 `tools_work/issue1/_audit_forward_vars.cjs`（luaparse AST 取函数体范围 + 收集真实读写标识符），并做**负向对照**证明它真能抓到。结果：164 个顶层函数，0 隐患 |

> 负向对照第一版曾用「把 GAME 整表挪到文件末尾」，那样文件直接语法错误，脚本红了但**红的原因不对**。
> 重写成语法合法的最小例后才可信 —— **「红得不对」的对照等于没验**。

### 本轮修掉的 3 个真实缺陷（Lead 直接改）

#### ① P0 结算面板**整块不可点**

| 项 | 内容 |
|---|---|
| 现象 | 点「再来一局」「复盘」都**没有回调、没有点击音效**；但控件树里两个命中区与全屏遮罩命中区**都是 `active=true`** |
| 根因 | `UI.result.hitOverlay` 是 `1600×900` **全屏**命中区（`create_cursor_area{x=0,y=0,w=canvasW,h=canvasH}`），作用是吃掉面板外的点击。而 `raise_modal_hits()` 与 `build_all_ui` 里都把它**最后**抬起 —— `SetAsLastSibling` 是「后抬起的在上层」，于是它盖住了两个按钮 |
| 修法 | 两处都改成 `{ hitOverlay, hitAgain, hitReview }` 顺序：**全屏遮罩先抬（压最底），按钮后抬盖住它** |
| 为什么之前没发现 | 我前一轮把「点 (938.4,379) 时 `50919` 在响」误当成点击音 —— 那其实是**结算出现音**。真正的点击音是 `50888`。**读数不能只看「有没有声音」，要看是哪一个 id** |

#### ② P1 结算「复盘」在一步未走时**静默失效**

| 项 | 内容 |
|---|---|
| 现象 | 0 步求和后进结算，点「复盘」无反应、无日志 |
| 根因 | `enter_review(allowEmpty)` 里 `local empty = (#GAME.history <= 1)`；`if empty and not allowEmpty then return false end`。结算面板回调写的是 `enter_review()` → `allowEmpty` 为 nil → 静默 `return false` |
| 修法 | 结算面板改 `enter_review(true)`（理由：复盘价值不只在回看走子，还包括「从当前局面开新局」；一步未走正是从开局摆变化，与入口 2 语义一致）。**对局中的「看历史」仍传空** —— 那里「没得复盘」是正确提示 |
| 连带的坑 | 修完发现「退出复盘」会错误地跳回**初始界面**：因为 `exit_review` 用 `allowEmpty` 判「是不是从菜单进来的」。两处语义被复用 → 新增独立字段 `GAME.review.fromMenu`，只在 `entry_start_review` 里置 `true` |

#### ③ P1 「自检 30/30」曾经是**从未执行**的假绿

| 项 | 内容 |
|---|---|
| 现象 | 块 1~5 我一直报「自检 N 条全绿」，但日志里**从来没有自检输出** |

## 贯穿 v2.0 的三条流程教训

### ① 三级证据强度（design-lead 提出，已写入导入方案）

> **① 真机实跑 > ② 模拟器实跑 > ③ 读源码 / grep 特征名**
> 凡标「③」的结论，**只能判断「有没有这段代码」，不能判断「功能能不能用」**。

本项目真实发生过：某版源码能搜到 40+ 处新功能特征名，看起来「都同步了」，**但脚本启动第一步就崩了**。
静态检查当时是绿的，游戏是开不起来的。

### ② 「红得不对」的对照等于没验

`_audit_forward_vars` 的负向对照第一版让文件语法错误，脚本确实红了 —— 但红的原因是解析失败，不是检出前向引用。
**做负向对照必须证明「红的理由正确」。**

### ③ 并发开发期间任何「多副本对比」都是瞬时结论

docs-lead 曾报「`out/交付包/` 仍崩」，那是我实测之前 4 分钟的快照；lua-lead 已在其间跑完同步。
**报这类结论必须带核对时刻 + 文件 mtime。**
