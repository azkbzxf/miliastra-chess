> 供 docs-lead 回填 `out/交付包/导入方案.md` 第 7.7 节与附录 B.4。
> 实现来源：`lua/levelScript.lua` 的 `CONFIG.EV_*` 与 `net_on_signal()`。

## 一、信号基础

| 项 | 值 |
|---|---|
| 信号名 | `ChessSync` |
| 参数个数 | **固定 5 个**：`(eventType, a, b, c, fen)` |
| `eventType` | 整数，见下表 |
| `a` / `b` / `c` | 整数，含义随 eventType 变 |
| `fen` | 字符串，当前所有事件都传 `""`（预留给将来用 FEN 同步整局） |
| 服务端行为 | 收到即**广播给房间内所有人，包含发送者自己** |

> ⚠️ 「包含发送者自己」这一点决定了**每个事件都必须做回声过滤**，见第三节。

### 2.3 `EV_RESIGN` 的两种语义（v2.0 重要变更）

同一个 `eventType = 2`，靠 `c` 区分：

| c | 语义 | 触发场景 | 对端结算文案（逐字） |
|---|---|---|---|
| **0** | **认输** | 对局中主动点「认输」并确认 | 白方认输 → `白方认输，黑方胜` / `白方点了认输`<br>黑方认输 → `黑方认输，白方胜` / `黑方点了认输` |
| **1** | **弃局** | 对局中点「返回主菜单」→ 确认放弃 | `对手已离开本局` / `本局结束，不计胜负` |

> **为什么必须区分**：认输是「我下不过你」，弃局是「我走了，这局不算数」。
> 若把弃局显示成「对方认输，你胜了」，玩家会误以为赢了一盘真棋。

**触发条件（代码位置：`back_to_main_menu`）**：
```lua
if GAME.screen == "playing" and not GAME.over and not GAME.localMode then
  net_send_event(CONFIG.EV_RESIGN, (GAME.mySide == 1) and 0 or 1, 0, 1, "")
end
```
三个条件缺一不可：**对局中** + **未结束** + **联机**（同屏单人没有对端，不发）。

## 三、回声过滤（逐事件）

服务端「收到即广播给所有人（含发送者）」⇒ 每个事件都必须能识别并丢弃自己的包。

| 事件 | 过滤依据 | 为什么这样做 |
|---|---|---|
| `EV_MOVE` | `GAME.lastSentMove{from,to,promo}` 三项精确匹配 → 匹配上只清标记不处理 | 本地已 `apply_move`，再按「对方走子」重算必然找不到合法走法（起点格已空），会误报错 |
| `EV_NEWGAME` | 无（幂等） | `new_game()` 重复调用结果相同 |
| `EV_RESIGN` | `GAME.over == true` 则 return | 自己收到自己的弃局包时本端已结束 |
| `EV_DRAW_REQ` | `GAME.drawReqSent` 标记 | 不加过滤会让发起者自己弹「对方想和棋」，自己问自己 |
| `EV_DRAW_ACC` | `GAME.over` 挡住重复结算 | 同意方已本地结算 |
| `EV_DRAW_NO` | 无副作用 | 只改提示条 |
| `EV_ROLE` | 无（幂等） | 重复赋值同一个身份 |
| **`EV_READY`** | **无需过滤（幂等）** | 只会把 `peerReady` 再设一遍，无副作用。注意不能把它当作「对手在线」的证据（自己的包也回来），故 `peerSeen` 只在 `not peerLeft` 时置位 |
| **`EV_START`** | **`GAME.screen == "playing"` 则 return** | 已在对局中就说明已经开过局，重复包丢弃 |
| **`EV_UNDO_REQ`** | **`pendingUndo.byMe == true` 则 return** | 我是发起方，收到自己的请求不能弹「对方请求悔棋」 |
| **`EV_UNDO_ACC`** | **`pendingUndo == nil` 则 return** | 执行时会清空 `pendingUndo`，所以自己的 ACC 播回来时它已是 nil |
| **`EV_UNDO_NO`** | **`pendingUndo == nil` 或 `byMe == false` 则 return** | 只有「我发起的请求」才该被拒绝信号影响 |

## 四、两端状态一致性怎么保证

### 4.1 悔棋：为什么必须由 `EV_UNDO_ACC` 驱动，而不是发起方本地先撤

**如果发起方点确认就本地撤回**，会出现这个序列：

```
发起方：点确认 → 本地撤回 2 手（棋盘已经变了）
        → 广播 EV_UNDO_REQ
响应方：收到请求 → 点「拒绝」
        → 广播 EV_UNDO_NO
发起方：收到 NO → 但已经撤回了，无法恢复
结果：发起方棋盘退回 2 手，响应方棋盘还在原处 → **局面分叉**
```

**正确做法**（当前实现）：

```
发起方：点确认 → 只置 pendingUndo={byMe=true,t=0} + 广播 EV_UNDO_REQ
        （局面一字未动，棋钟冻结）
响应方：收到 REQ → 弹框
        ├ 同意 → 广播 EV_UNDO_ACC → 本地执行撤回
        └ 拒绝 → 广播 EV_UNDO_NO  → 本地不动
发起方：收到 ACC → 本地执行撤回（扣 1 次）
        收到 NO  → 解冻，次数不扣
```

- **唯一的执行触发点是 `EV_UNDO_ACC`**，两端都在「收到/发出它的那一帧」执行。
- **次数只绑在真正执行上**：请求被拒 / 超时 / 掉线，一律不扣。
- **超时兜底**：`UNDO_REQUEST_TIMEOUT_SEC = 15` 秒没收到任何回应 → 视同拒绝，解冻，不扣次数。
  没有这条，对方掉线会让人永远卡在冻结状态。

### 4.2 开局时机：倒数结束立即本地开局，`EV_START` 只是通知

**当前实现（v2.0 方案 T，已取代早期的「方案 A」）**：
```
双方就绪 → 各自跑 3 秒倒数（纯视觉）
         → 倒数跑完 → **立即本地进 playing**（不等任何网络包）
         → 然后 fire-and-forget 广播 EV_START 通知对端
         → 对端收到 EV_START → 若还在 lobby 就跟着进 playing
```

**为什么从「等 EV_START」改成「先开局再通知」**：
早期方案把 `EV_START` 当成**开局的前置条件**，于是对端掉线 / 没搭节点图时，
本端会卡在「等待对端超时」这个中间态里（实测日志出现过：
`等待对端 EV_START 超时（1.5 秒），本地直接开局`）。
现在 `EV_START` 退化为**纯通知**，不再是条件，本端永远不会被对端的网络状况阻塞。

**代价**：两端开局时刻可能差一个网络往返（~100ms）。
这可以接受 —— 对局第一手要等玩家思考，100ms 差值无人能感知；而「卡住不动」是明显的坏体验。

> 注：`LOBBY_START_GRACE_SEC`（原 1.5 秒宽限期）已随该逻辑删除，不再存在。

`EV_START` 由倒数先跑完的那一端广播，另一端收到就跳过自己的剩余倒数。
两端各跑完倒数时**各自**广播一次（因此可能出现 2 条，幂等无害）。

### 4.3 时间档「先选者生效」

`EV_READY` 的 `b` 携带档位号，这是「先选者生效」的载体：

```
收到 EV_READY(a=准备位, b=档位号):
  if not GAME.lobby.tcLocked then        -- 本地还没锁
      apply_time_control(b)              -- 采用对方档位
      GAME.lobby.tcLocked = true
      GAME.lobby.tcOwner = 2             -- 记为「对方选的」
  end
  -- 已锁定 → 忽略 b，只更新 peerReady（先选者优先）
```

对应断言 `ev_ready_ignores_when_locked`，双向验证：
① 未锁定 → 档位**确实变了** + 已锁定 + `tcOwner=2`
② 已锁定 → 档位**确实没变**，且用 `peerReady` 被改来证明「信号确实被处理了」
（否则「没变」可能只是因为压根没收到这条信号 —— 那是假绿）

## 五、单人兜底

**联机信号全部是可选增强，不是必需品。** 没有任何服务端节点图时：

| 场景 | 行为 |
|---|---|
| `net_send_event` 发不出去 | 内部 `pcall` 吞掉，不影响游戏逻辑 |
| 待机室没人握手 | 15 秒后提示「没等到另一位玩家，也可以直接开始」，「直接开始」全程可用 |
| 双方就绪但收不到 `EV_START` | 1.5 秒宽限期后自己开局 |
| 悔棋 | 同屏模式直接本地执行，完全不经过信号 |
| 悔棋请求没人回应 | 15 秒超时后解冻，不卡死 |

对应断言 `lobby_solo_not_blocked_by_signals`。

## 六、断言覆盖

| 断言名 | 守什么 |
|---|---|
| `online_undo_sequence` | ① 请求时本地不撤 ② ACC 回退两步且扣次数 ③ NO 全不变且不扣次数 |
| `ev_ready_ignores_when_locked` | 先选者生效，已锁定不被覆盖 |
| `lobby_solo_not_blocked_by_signals` | 单人路径不依赖信号 |

> 三条断言都遵守同一条纪律：**「A 不应改变 B」必须同时断言「A 确实做了事」**，
> 否则 A 完全没生效时断言会全绿（假绿）。
