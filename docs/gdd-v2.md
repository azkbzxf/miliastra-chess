### 1.2 4 个已拍板语义决策（原文照录，不得改动）

1. **走时档位：4 档，无自定义** —— 超快棋 1+0 / 闪电战 3+2 / 快棋 15+10 / 慢棋 90+30（分钟+每步加秒）。联机时以**先选者**为准。
2. **复盘中局研习**：逐手回放 + **分支试走**（可在任意历史局面下试走看变化，不改主变），且可从任意一步「从此局面开新局」。
3. **联机形态**：千星没有跨房间匹配服务器。联机 = 同一关卡内的**待机室**：玩家进关卡即进待机室，双方各点「准备」，两人都准备好后 3 秒倒数开局。时间档先选者生效。
4. **悔棋**：**成对悔棋**（双方各退一步，回到己方上一步之前的局面），**每方每局限 3 次**，联机需对方同意。

> 决策 3 的「玩家进关卡即进待机室」在实际界面流程里落地为：**进关卡 → 初始界面 →（点「联机·待机室」）→ 待机室**。因为初始界面本身承载「选时间档」这一步，玩家不可能跳过它直接进待机室。三入口并行是用户需求 1 的 ①②③ 三条并列项，所以初始界面必须先于待机室。**这里的「即」解作「联机没有第二跳（没有房间列表/匹配队列），点一下就在关卡里的待机室」，不是「不用经过初始界面」。**

### 1.3 本轮的 6 个设计判断（需 Lead 知悉；1–3 建议保留，4–6 是低风险收口）

| # | 判断 | 理由 | 影响面 |
|---|---|---|---|
| D-1 | **悔棋只能由「当前轮走方」发起**；本方刚走完那一刻按钮不可用 | 若允许「刚走完的一方」悔棋，撤回的 2 手包含对手上一步 —— 对手会**先看到我的走法再被撤走并重想**，这是信息泄露（v1 附录 C 拒做悔棋的全部理由）。限定轮走方发起后，撤回的 2 手都是对手已经看过的内容，零信息泄露。副作用：本方走臭棋要等对手走一步才能悔 —— 但这正是「成对」的代价，且与 H-4「双方各退一步」完全自洽 | 悔棋可用性、文案「等轮到你时再悔棋」 |
| D-2 | **悔棋请求挂起期间冻结双方棋钟，15 秒不回应视为拒绝** | 冻结避免「请求者自己的钟被对方挂机烧掉」；15 秒上限 + 每方 3 次把最大冻结时长锁死在 45 秒/方/局，不可被刷 | `UNDO_REQUEST_TIMEOUT_SEC`、`OnUpdate` 判定 |
| D-3 | **待机室不显示玩家昵称**，玩家行标签用「你 / 对手」，未检测到对手时该行显示 `等待对手加入…` | 客户端 Lua **无法读取房间成员列表与他人昵称**（见 10.2 的 U-1）。写「玩家1 / 玩家2」会暗示顺序一致，而实际不可保证 —— 用「你 / 对手」只表达「本端视角」，不会骗人 | 待机室玩家行文案（5 个逐字值已定死，见 5.3） |
| D-4 | **对局中不提供「返回主菜单」**；`返回主菜单` 出现在①结算弹窗（三键）②复盘研习（替换「退出复盘」） | 对局中允许一键回菜单 = 允许「借口换档逃局」。想换时间档必须先把这一局结束，这是棋类游戏的标准做法。**替代路径见下方 1.3.1** | 结算弹窗三键布局 |
| D-5 | **保留「切换本地同屏 / 切换联机对战」按钮不动** | 它是「用户没搭服务端节点图时也能玩」的唯一入口，已在 v1 交付文档和 `docs/沙箱能力清单.md` 里对用户承诺过。v2.0 动它会连带作废 `导入方案.md` 的一段说明 | 面板 11 项排布不变 |
| D-6（**降级为建议，非契约**） | *建议*慢棋档的「预计单局时长」标注成 `2 小时以上` 一类的量级提示 | 严格推演上界是 230 分钟（见 4.3），但那是「双方都用满首钟」的极端值，实际对局普遍短得多；写成「1.5–4 小时」会把新手吓到直接选快棋。**`est` 是界面文案、不参与任何判定、不影响任何用例**，属主观估计 —— 本文件**不对 `est` 做契约约束**，最终取值由实现方与产品判断决定 | 仅界面文案，无逻辑影响 |

> **`est` 的定性（重要）**：`est` 四个字符串**不是可测契约**。本文 4.1 / 4.3 / 12.1.5 里给出的数字只是**推算依据的展示**与**建议值**；实现方定下别的数字时，**以实现为准**，本文件随之更新，不构成缺陷。
> 本文件真正约束的是 4.1 表的**前五列**（`n` / 名称 / 首钟秒 / 每步加秒 / 显示形式）—— 那是 H-1 硬契约。

#### 1.3.1 D-4 的替代路径：对局中想换时间档怎么办

若采纳 D-4（对局中不给「返回主菜单」），玩家想换档必须走完**三步**：

```
对局中想换档
  → ① 点「认输」→ 确认框「认输就直接判负，确定吗」→ 确定认输
  → ② 结算弹窗 → 点「返回主菜单」
  → ③ 初始界面 → 重新选档位卡 → 重新选入口
```

- **成本评估**：3 步 + 1 个确认框。第 ① 步会**明确告知代价**（「认输就直接判负」），这是刻意的 —— 换档等价于弃掉当前这局，玩家应当被明确告知。
- **为什么不做「对局中一键回菜单 + 二次确认」**：那样「弃局换档」的代价只剩一次点击，玩家会养成「下臭了就换档重开」的习惯。棋类游戏里，一局的价值正来自它不可轻易反悔。
- **若产品最终决定「对局中也给返回主菜单」**（Lead 实测已实现）：本文件**接受该实现**，但要求两条不因放宽而丢：
  1. 保留确认框文案 `回主菜单会放弃这一局，确定吗`（已实现 ✅）；
  2. **该动作必须同时广播 `EV_RESIGN`** —— 否则联机对手会看到一个突然消失的对手、局面悬空。这是替代路径下唯一需要额外约束的一条。

## 二、界面流程图（文字版状态机）

### 2.1 五个界面

```
GAME.screen ∈ { start, lobby, playing, result, review }
```

> **与 `GAME.state` 是两件事，绝不合并。**
> `GAME.state` = 脚本生命周期（NEW / STARTING / RUNNING / FAILED / DESTROYED）；
> `GAME.screen` = 玩家在哪个界面。合并会让自检里守着「脚本活着」的断言在进初始界面时变红。

| 界面 | 棋盘 | 侧面板 | 初始界面层 | 待机室层 |
|---|---|---|---|---|
| `start` | 隐藏 | 隐藏 | **显示** | 隐藏 |
| `lobby` | 隐藏 | 隐藏 | 隐藏 | **显示** |
| `playing` | 显示·可点 | 显示·可点 | 隐藏 | 隐藏 |
| `result` | 显示·不可点 | 显示·命中区关闭 | 隐藏 | 隐藏 |
| `review` | 显示·**可试走** | 显示·复盘键位 | 隐藏 | 隐藏 |

### 2.4 禁止的转移与理由

| 禁止 | 理由 |
|---|---|
| `start → result` | 没下过棋不可能有结算 |
| `lobby → result` | 同上 |
| `result → lobby` | 联机对局结束后想再联机必须回主菜单重走待机室（否则「对手掉线后卡在待机室」） |
| `review → lobby` | 复盘与联机是两条独立路径 |
| 任意界面 → `playing` 且不经过开局重置 | 会造成「旧 history + 新棋钟」的半状态 |
| 弹窗打开时改 `GAME.screen` | 与 v1.10 的模态弹窗双层防线同源：`confirmKind ~= nil` 时一律不改 screen |

## 三、初始界面（Start Screen）视觉规格

### 3.1 设计意图

- **不做装饰图、不做插画、不做卡片底板**。视觉层次全靠「标题字号差 + 元素间距 + 描边」建立。
  理由：初版曾考虑给整块内容加一张浅卡片底，但 `PANEL_BG`(252,250,247) 与外壳 `BG`(242,239,234) 只差约 10 点亮度 —— 平台文本框没有 `border` 字段，必须再拼一圈描边色块才分得出来（v1.10 面板已经踩过一次），加一层就多一层糊掉的风险，收益只是「看起来更整」。
- **背景 = 复用现有 24 条插值色带**（`BG_TOP → BG → BG_BOTTOM`），一条控件都不新建。
  v1.10 实测相邻带最大通道差 = 1，肉眼连续，**不会出现「纯色块拼接的硬横线」**。
- 「适配棋盘」的含义是**同一间棋室的同一个色温**：初始界面的暖米底 → 点入口后棋盘带着暖木外框浮上来，两者是同一个空间，不做场景切换动画。

### 4.1 四档定义：`CONFIG.TIME_CONTROLS`

**前五列是 H-1 硬契约，不得改动。最后一列 `est` 是界面文案，以实现为准（见 1.3 的 D-6）。**

| n | 名称 | 首钟（秒） | 每步加秒 | 显示形式 | 卡上三类文案（名称/首钟/加秒为契约，`est` 为建议值） |
|---|---|---|---|---|---|
| 1 | 超快棋 | **60** | **0** | 1+0 | `首钟 01:00` / `无加秒` / `预计 1–3 分钟` |
| 2 | 闪电战 | **180** | **2** | 3+2 | `首钟 03:00` / `每步 +2 秒` / `预计 5–12 分钟` |
| 3 | 快棋 | **900** | **10** | 15+10 | `首钟 15:00` / `每步 +10 秒` / `预计 15–40 分钟` |
| 4 | 慢棋 | **5400** | **30** | 90+30 | `首钟 1:30:00` / `每步 +30 秒` / `预计 60–120 分钟` |

- **`n` 是协议字段**：随 `EV_READY` 的 `c` 参数与 `EV_START` 的 `b` 参数下发。

| 档 | 对应赛制 | 说明 |
|---|---|---|
| 超快棋 1+0 | 线上通行的 **Bullet（子弹棋）** | FIDE 无对应正式赛制；FIDE 最快的正式赛制是 Blitz 3+2 |
| 闪电战 3+2 | **FIDE 世界闪电战锦标赛**（World Blitz）| 3 分钟 + 每步 2 秒 |

### 4.3 `est` 的推算依据（**仅供理解，不是契约**）

统一假设：**每方 50 步、首钟用尽、加秒全部计入**。这张表只说明「上界能到多少」，帮实现方判断
`est` 该给什么量级；**实际取值以实现为准**（D-6）。

| 档 | 每方上界 `首钟 + 50×加秒` | 每方 | 全场（上界） | 上界的性质 |
|---|---|---|---|---|
| 1+0 | 60 + 0 = 60 s | 1.0 min | **2.0 min** | 真上界（无加秒、无悬念） |
| 3+2 | 180 + 100 = 280 s | 4.7 min | **9.3 min** | 双方都用满首钟才达到 |
| 15+10 | 900 + 500 = 1400 s | 23.3 min | **46.7 min** | 同上 |
| 90+30 | 5400 + 1500 = 6900 s | 115 min | **230 min ≈ 3.8 h** | 同上，且实际极少达到 |

- **上表是「上界」，不是「预计」**。`est` 要表达的是「常见对局多长」，与上界不必然相同 —— 这正是 D-6 把 `est` 降级为建议的理由。
- 当前实现取 `1–3 / 5–12 / 15–40 / 60–120 分钟`，与上界量级同阶，**本文件接受，不构成缺陷**。
- 可选的量级提示（建议，非契约）：慢棋档若想更诚实地表达不确定性，可用 `2 小时以上` 一类的写法；`2 小时` 与上界 3.8 小时并不冲突，因为它只是「常见量级」的下沿。

### 4.4 棋钟派生规则（取代 v1 的 5.2）

| 项 | v1.12 | v2.0 | 快棋档（默认）是否改变 |
|---|---|---|---|
| 每方初始 | 900 | `GAME.tcInitial` | 900 → **不变** |
| 每步加秒 | 10 | `GAME.tcIncrement` | 10 → **不变** |
| 封顶 | 1800 | **`首钟 × 2`** → 120 / 360 / 1800 / 10800 | 1800 → **不变** |
| 告急音效阈值 | 30 s | `max(10, min(30, floor(首钟/10)))` → 10 / 18 / 30 / 30 | 30 → **不变** |
| 数字变红阈值 | 60 s | `max(20, min(60, floor(首钟/5)))` → 20 / 36 / 60 / 60 | 60 → **不变** |
| 计时方式 | 逐帧累加 dt，不读现实时间 | **不变** | — |
| 显示格式 | `MM:SS` | **剩余 ≥ 3600 秒时用 `H:MM:SS`**，否则 `MM:SS` | 不变（< 3600） |

> **封顶为什么是「首钟 × 2」**：v1.12 的 1800 就是 `2 × 900`，即「最多存到两倍首钟」。按同一比例推广，四档全部自洽，且快棋档逐位不变。封顶在任何一档都不会被常规对局触及（见 4.3 的上界，都小于 2×首钟）。
> **告急/变红为什么按首钟派生**：超快棋 60 秒档如果沿用 60 秒变红阈值，**开局第一帧就是红的**；慢棋 5400 秒档如果沿用 30 秒响音，玩家会觉得「还没到时候」。派生后四档手感一致：都在「剩余约 1/10 ~ 1/5」时给压力。

|---|---|---|---|---|
| 1+0 | `白 01:00` | 7 | 168 px（字号 28） | ✅ 约 108 px |
| 3+2 | `白 04:40` | 7 | 同上 | ✅ |

| 90+30 | `白 1:30:00` | 9 | 同上 | ✅ 约 138 px |

### 4.6 联机同步与「先选者生效」

| 步骤 | 谁做 | 做什么 |
|---|---|---|
| ① | 任一方点档位卡 | 立即广播 `EV_READY(a=身份, b=就绪状态, c=档位号)` —— **每次状态变化都广播全量状态**，不增量、不差分 |
| ② | 收到 `c` 的一侧 | 若本端尚未锁定，则 `apply_time_control(c)` 覆盖；标记「档位已锁定」+「由对手选定 / 由你选定」 |
| ③ | 后点卡的一方 | 卡已置灰不可点，点了只弹提示条 `时间档已锁定，由对方选定` |
| ④ | 倒数完/直接开始 | 用 `GAME.tcInitial / tcIncrement` 开局，并广播 `EV_START(a=身份, b=档位号)` |

- **同时点击的兜底**：双方几乎同时点了不同档位（服务端延迟最低 100ms，实际很少发生）。判定规则写死为「**身份号小的一方（白方，`a=0`）胜出**」，其余一侧静默覆盖并记一条 `log_info`。这是确定性规则，可测。
- **为什么把档位塞进 `EV_READY` 而不新开事件**：待机室的全部状态就是一个二元组 `(就绪, 档位)`。每变一次就广播全量二元组，收到方直接覆盖 —— 幂等、自愈、不需要握手序号、不会因为丢一包而长期错位。

## 五、待机室（Lobby）视觉与交互规格

### 5.1 设计意图与能力边界（**必读**）

千星没有跨房间匹配服务器（H-6）。待机室就是**本关卡内的集合点**：两个玩家各自从初始界面点「联机·待机室」进来，靠服务端节点图把信号广播给房间内所有人（含发送者自己）来互相发现。

**能力边界（决定了这一整节的样子）**：

| 想要的能力 | 实际情况 | 后果 |
|---|---|---|
| 读取房间内玩家列表 | **未在官方文档中检索到**（客户端 API 无任何玩家列表/人数/昵称接口） | 「玩家列表」只能是「你」+「对手」两行，`对手` 一行由「是否收到过对方信号」来点亮 |
| 显示玩家昵称 | 同上，不可得 | 不显示昵称（D-3） |
| 「玩家进入关卡」事件 | **未在官方文档中检索到** | 靠信号握手 + 超时推算 |
| 精确的就绪/离开通知 | 有 `ServerSignal` 双向通道 | 用 `EV_READY` 全量广播 |

**握手机制（两包互认）**：

```
我进待机室       →  广播 EV_READY(我, 就绪=0, 档位=n)     ← 第 1 包
对方收到第 1 包  →  若尚未应答过：广播 EV_READY(对方, 就绪=0, 档位=n)  ← 第 2 包
我收到对方的包   →  点亮「对手」行，把对手的就绪状态写进界面
```

- 之后**每一次状态变化（准备/取消/改档）都再广播一次全量状态**，所以握手包丢了也会被后续包补上。
- 15 秒内一包都没收到 → 「对手」行保持 `等待对手加入…`；提示条此时**不显示等待句**，而是在 15 秒后切到 `没等到另一位玩家，也可以直接开始`（5.7）。
- **数字自检**：服务端延迟最低 100ms（《客户端控件和客户端脚本》第五节 1）→ 握手 2 包最坏 200ms 完成，15 秒超时余量 75 倍。

### 5.3 玩家行（`PLAYER1` / `PLAYER2`）

单行文本框，内容格式固定为：

```
{标签}　{状态}
```

| 行 | 标签（逐字） | 状态取值（逐字） | 说明 |
|---|---|---|---|
| `PLAYER1` | `你` | `已准备` / `未准备` | 恒为本端玩家；本端未准备时也显示 `未准备`（不显示「等待」） |
| `PLAYER2` | `对手` | `已准备` / `未准备` / `等待对手加入…` | 未收到任何对方信号时为 `等待对手加入…` |

**定死的 5 个逐字值**（Lead 已指定，供 Lua 与 Demo 两侧对齐）：

| 键名 | 逐字 | 用在哪 |
|---|---|---|
| `LOBBY_ME` | `你` | `PLAYER1` 行标签 |
| `LOBBY_OPP` | `对手` | `PLAYER2` 行标签 |
| `LOBBY_SLOT_EMPTY` | `等待对手加入…` | `PLAYER2` 行的状态（未检测到对手时） |
| `LOBBY_READY_ON` | `已准备` | 任一行的状态（该方就绪时） |
| `LOBBY_READY_OFF` | `未准备` | 任一行的状态（该方未就绪且对方已在线时） |

> 末字是**省略号 `…` U+2026**（单个字符），不是三个半角句点 `...`。整个字符串 6 个字符。
> **`等待玩家进入…` 不再使用** —— 待机室的「等」只有一处，就是 `PLAYER2` 行；提示条用 `没等到另一位玩家，也可以直接开始`（见 5.8）。原先那个独立的提示条等待文案已删除，避免两条几乎重复的「等待」让玩家分不清该看哪个。

- 中间是全角空格 `U+3000`。
- **不显示昵称、不显示头像、不做序号**（D-3）。
- `你` 行的身份标注：在 `ROOM_TC` 行末尾追加 `（执白）` / `（执黑）`，格式见 5.4。
- 就绪状态**不额外画勾选图标**：平台没有内置对勾图元，纯图元画勾要 2–3 个控件，收益只是好看。靠文字 + 颜色（`已准备` 用 `TEXT_ACCENT` 琥珀、`未准备` 用 `TEXT_SUB`）已经一眼可辨。

### 5.4 时间档锁定显示规则（`ROOM_TC`）

单行，格式固定：

```
时间档 {档位名} {首钟}　{归属}
```

| 归属取值（逐字） | 出现条件 |
|---|---|
| `还没人选` | 双方都没点过档位卡 |
| `由你选定` | 本端点过，且本端广播先到（或双方同时点且本端为白方） |
| `由对手选定` | 收到对方的档位广播，且本端未锁定 |

示例：`时间档 快棋 15:00　由你选定`

- 一旦有人选定，4 张档位卡**全部置灰不可点**（底 `BTN_DIS_BG`、字 `BTN_DIS_TEXT`），点击只弹提示条 `时间档已锁定，由对方选定`。
- 身份标注放在 `TITLE` 行右侧：`（执白）` / `（执黑）`。若身份未定（收不到 `EV_ROLE`），显示 `（身份待定）`。

### 5.5 准备流程

| 状态 | `READY_BTN` 文案 | 点下去的效果 |
|---|---|---|
| 未准备 | `准备` | 本地就绪=1，广播 `EV_READY` |
| 已准备 | `取消准备` | 本地就绪=0，广播 `EV_READY`；若倒数中则中止倒数 |

- **只有 1 人时按「准备」也合法**：状态记着，对手进来后握手包会把它带过去。不能按「没人就不给准备」，否则对局永远开不了。
- **双方都就绪** 是唯一的开局条件（`T-06`）。判定在 `OnUpdate` 里读两个布尔量，不排队列。

### 5.6 3 秒倒数（`COUNTDOWN`）

| 时刻 | 显示 | 备注 |
|---|---|---|
| t ∈ [0, 1) | `3` | 字号 `FONT.LOBBY_COUNTDOWN` = **48**，居中 |
| t ∈ [1, 2) | `2` | 同上 |
| t ∈ [2, 3) | `1` | 同上 |
| t = 3 | 开局 | 广播 `EV_START`，进 `playing` |

- **字号 48 的来历（一次真实的踩坑，勿改回 72）**：
  本槽板高 `0.115 × 900 = 103.5px`；按 6.7 的通用规则（板高 ≥ 2.1 × 字号），
  `103.5 / 2.1 = 49.3` → **最大只能用 49px**。曾写 72，72 × 2.1 = 151.2 > 103.5，
  **差 47.7px，结果是整行被吞掉、什么都不显示、也不报错**（本项目第三次踩 D-02）。
  取 **48**：48 × 2.1 = 100.8 ≤ 103.5 ✅，留 2.7px 余量。
- **为什么不把板高扩到 0.168 去容 72 号字**：那会把 `COUNTDOWN` 的区间从 [0.700, 0.815] 顶到 [0.700, 0.868]，
  与 `TITLE` 的 [0.830, 0.915] **相交**，必须连带改 `TITLE`/`ROOM_TC`/`PLAYER1`/`PLAYER2` 五项 —— 改一处引发五处，
  而 48px 在 1600×900 上对比面板棋钟 28px 已经足够醒目。**改字号不动布局，风险最小。**
- 数字用 `math.floor(3 - t)` 取，**逐帧累加 dt**，不读 `os.time`（`OnUpdate(dt)` 不受关卡时停影响，这是 v1 棋钟的同一条确定性纪律）。
- 倒数期间显示 `准备开局`（`HINT` 行），且 `READY_BTN` 变 `取消准备`，`SOLO_BTN` 置灰不可点（避免「倒数中还能直接开始」造成双开局）。
- **倒数中取消**：任一方取消准备 → 立即清倒数计时器、`COUNTDOWN` 清空、`HINT` 显示 `已取消准备，等待重新准备`，回到等待态（`T-07`）。
- **开场音**：倒数每跳一个数字播一次 `CLICK`（50888）。t=0 开局时播 `SELECT`（50894）。**不新增音效 ID**（见 10.3）。
- **两端的倒数不必严格同帧**：`EV_START` 会强制对齐 —— 谁先倒数完谁广播，对方收到即刻开局，不等自己的倒数。最坏偏差 = 一个信号往返（≥100ms，实测通常 <200ms），对面 60 秒的超快棋档也只有 0.3% 的误差。

### 5.7 待机室完整状态机（**实现与 runCase 的共同依据**）

这一节是待机室的**逐条状态转移表**。`lua-lead` 按它实现块 2，步骤 6 按它写 `runCase`。

#### 5.7.1 状态定义

| 状态 | 含义 | 判定量（本端） |
|---|---|---|
| `L0 无人` | 进了待机室，**从未收到过任何对方信号** | `LOBBY.peerSeen == false` |
| `L1 对手在·双方未备` | 已收到过对方信号，对手未就绪 | `peerSeen == true ∧ myReady == false ∧ peerReady == false` |
| `L2 我已备·对手未备` | 我准备好了，对手还没 | `peerSeen ∧ myReady ∧ ¬peerReady` |
| `L3 对手已备·我未备` | 对手准备好了，我还没 | `peerSeen ∧ ¬myReady ∧ peerReady` |
| `L4 双方就绪` | 双方都准备好了 | `peerSeen ∧ myReady ∧ peerReady` |
| `L5 倒数中` | 已进 3 秒倒数 | `countdownT < LOBBY_COUNTDOWN_SEC`（`L4` 的子态） |
| `L6 已开局` | 已进 `playing` | `GAME.screen == "playing"` |

> 两个内部量：`LOBBY.peerSeen`（布尔，收到过对方信号即为真，**之后不再复位**，除非收到 `b=0` 的离开包）、
> `LOBBY.countdownT`（秒，逐帧累加 `dt`）。
> **`peerSeen` 是「曾经见过」而不是「现在在线」** —— 因为读不到玩家列表（U-1），我们无法知道对手是否还在，
> 只能靠「他有没有继续发信号」推断。这个区别决定了 `L1~L4` 在对手掉线时的行为（见 5.7.3 的 R-08/R-09）。

#### 5.7.2 转移表（一行一个转移）

| # | 状态 A | 触发 | 状态 B | **可观察结果**（玩家在这一帧看到什么） |
|---|---|---|---|---|
| **T01** | — （从初始界面点「联机·待机室」） | 进入待机室 | `L0` | 进 `screen="lobby"`。`对手` 行 = `对手　等待对手加入…`；`你` 行 = `你　未准备`；准备键 = `准备`；底部 = `双方都点准备后开始`；提示条 = **空**；倒数槽 = **空**；`直接开始` 可用。同时广播第 1 包 `EV_READY(a=我, b=0, c=档位)` |
| **T02** | `L0` | 收到对方第 1 包 `EV_READY`（非回声） | `L1` | `peerSeen = true`。`对手` 行 = `对手　未准备`。**并立即回发第 2 包**（若本端尚未应答过）。这是「我怎么知道别人进来了」的唯一途径 —— 没有玩家列表，只有信号 |
| **T03** | `L0` | 我先发了包，但 15 秒内一包都没收到 | `L0`（超时态） | `对手` 行**仍是** `对手　等待对手加入…`（事实如此）；提示条切到 `没等到另一位玩家，也可以直接开始`（此后常驻）。底部行**不变** |
| **T04** | `L1`/`L2`/`L3` | 点准备键（本端 未准备→已准备） | `L2`（对手未备）或 `L4`（对手已备） | 本端 `你` 行 = `你　已准备`（琥珀色，`LOBBY_READY_ON`）；准备键变 `取消准备`；广播 `EV_READY(b=1, c=档位)`。**对手端**随后看到 `对手　已准备` |
| **T05** | `L2` | 点准备键（本端 已准备→未准备） | `L1` 或 `L3` | 本端 `你` 行 = `你　未准备`（灰色）；准备键变 `准备`；广播 `EV_READY(b=0, c=档位)`。若当时在 `L5`，**同时中止倒数**（见 T09） |
| **T06** | `L1`/`L2` | 收到对方 `EV_READY(b=1)`（非回声） | `L3` 或 `L4` | 对手行 = `对手　已准备`（琥珀）；**若本端也已准备则进 `L4`** |
| **T07** | `L3`/`L4` | 收到对方 `EV_READY(b=0)`（非回声） | `L1` 或 `L2` | 对手行 = `对手　未准备`（灰）；若在 `L5` 则中止倒数（见 T09） |
| **T08** | `L4` | 双方就绪成立的那一帧 | `L5` | 倒数槽开始显示 `3`；提示条 = `准备开局`；`直接开始` **置灰**；准备键仍为 `取消准备`（可取消）。累计 `countdownT` |
| **T09** | `L5` | 任一方取消准备（本地点击 或 收到 `EV_READY(b=0)`） | 回落 `L1`/`L2`/`L3` | **倒数槽立即清空**（`countdownT = 0`）；提示条 = `已取消准备，等待重新准备`；`直接开始` 恢复可用。**两端都必须回落到非 `L5` 态**，不许一端还在倒数 |
| **T10** | `L5` | `countdownT` 累加到 3 | `L6` | 进 `screen="playing"`；按锁定档位开局；广播 `EV_START(a=我, b=档位)`；播 `SELECT` |
| **T11** | `L4`/`L5` | 收到 `EV_START`（非回声，**不管本端倒数到没到**） | `L6` | **立刻进 `playing`**，不等自己的倒数。这是两端对齐的唯一保证 |
| **T12** | `L0` | 点「直接开始」 | `L6` | `localMode = true`，按当前档位（未锁则默认档 3）直接开局。**不广播 `EV_START`**（这是本机单人事，广播会让别人误开局） |
| **T13** | `L1`/`L2`/`L3`/`L4`/`L5` | 点「直接开始」 | `L6` | 同 T12。**注意**：此时房间里其实有对手，但玩家选择了单机 —— 允许，因为对手可能只是挂机；本端不广播 |
| **T14** | `L5` | 点「直接开始」 | `L5`（不变） | **无反应**（按钮已置灰）。防「倒数中还能直接开始」造成双开局 |
| **T15** | `L0`~`L5` 任一 | 点「返回主菜单」 | 回 `screen="start"` | 广播 `EV_READY(b=0)`（通知对手我不在了）；清 `peerSeen`/`countdownT`；**不弹确认**（待机室没有对局可丢） |
| **T16** | `L1`~`L5` | 收到对方 `EV_READY(b=0)` **且** 此后 15 秒再无对方任何信号 | 回落 `L0`（超时态） | `peerSeen` **保持 `true`**（他确实来过），但提示条切到 `没等到另一位玩家，也可以直接开始`；对手行**保持** `对手　未准备`（不退回 `等待对手加入…`，因为「他来过」是事实）。**见 5.7.3 的说明** |
| **T17** | `L0` | 点档位卡 | `L0` | 时间档行 = `时间档 {名称} {时刻}　由你选定`；广播 `EV_READY(c=新档位)`；4 张卡中其余 3 张置灰（本端已锁定） |
| **T18** | `L1`~`L5` | 点档位卡（档位已锁） | 不变 | 提示条 = `时间档已锁定，由你选定` 或 `时间档已锁定，由对方选定`（取决于谁锁的）；档位不变 |
| **T19** | `L0` | 收到对方 `EV_READY(c=n)` 且本端未锁 | `L0` | 时间档行 = `时间档 {名称} {时刻}　由对手选定`；本端档位被覆盖为 `n`；4 张卡置灰 |
| **T20** | `L0`~`L5` | 断线重连（控件全销毁重建） | 回 `L0` | 整个待机室回到初始状态（`peerSeen=false`）。**这是已知限制**（E-12），不做恢复 |

#### 5.7.3 八个边界情形的明确回答（Lead 点名要求）

| # | 情形 | 答案 |
|---|---|---|
| **B-1** | **我进关卡但没别人** | `L0`：`对手　等待对手加入…`、`你　未准备`、底部 `双方都点准备后开始`、提示条空、`直接开始` 可用。**可以点准备**（T04），只是没人看得见 |
| **B-2** | **别人进来，我怎么知道（读不到玩家列表！）** | **只靠信号**（T02）。他进待机室会广播第 1 包，我收到即 `peerSeen = true`、`对手` 行点亮。若两包都丢，我会一直停在 `L0`，**这就是为什么每次状态变化都重播全量包**（他一点准备我就又收到一包） |
| **B-3** | **我点准备** | 本端：`你　已准备` + 按钮变 `取消准备`（T04）。对方端：收到包后 `对手　已准备`（T06） |
| **B-4** | **对方点准备，我怎么知道** | 收到 `EV_READY(b=1)`（T06）。**若我此时也已准备，立即进 `L4` 并在同一帧起倒数**（T08） |
| **B-5** | **双方都准备，3 秒倒数期间能否取消** | **能**（T09 / T05）。任一方取消 → 倒数立即清空、提示条 `已取消准备，等待重新准备`、`直接开始` 恢复可用。两端同步回落 |
| **B-6** | **倒数中有人退出/掉线** | 退出者会发 `EV_READY(b=0)`（T15）→ 对方按 T09 中止倒数。**掉线（无信号）分两种**：<br>· **倒数中掉线**：本端倒数**照常走完并开局**（T10），因为已进 `L5` 说明双方都就绪过，且无法区别「掉线」与「网络抖动」；<br>· **开局后掉线**：交给 `EV_MOVE` 的既有超时逻辑（v1 的 30 秒无广播提示 `连接断了，可切到同屏`），**不在待机室范围** |
| **B-7** | **单人情况点「直接开始」** | T12：`localMode = true`，按当前档位开局，**不广播**。这是「不搭节点图也能玩」的兜底 |
| **B-8** | **15 秒没等到人，提示什么** | T03：提示条 = `没等到另一位玩家，也可以直接开始`（此后常驻）。`对手` 行**不变**（仍是 `等待对手加入…`）。底部行**不变** |

#### 5.7.4 两条必须写死的实现纪律

1. **`peerSeen` 收到任何对方信号都置 `true`，且不因「超时」复位**。
   超时只改**提示条**，不改 `peerSeen`、不改 `对手` 行 —— 否则对手稍微网慢一点，`对手` 行就在
   `等待对手加入…` 和 `未准备` 之间反复横跳，玩家会以为对面在反复进出。
2. **`L5` 的唯一出口是 T09（取消）、T10（倒数完）、T11（收到 `EV_START`）、T15（返回主菜单）**。
   不许有第五条路径 —— 尤其**不许在 `L5` 里因为「超时」自己跳出去**，那会造成一端开局一端没开。

### 5.8 单人兜底（`SOLO_BTN`）

- 文案恒为 `直接开始`，**始终可用**（除倒数中置灰）。
- 点下去：`localMode = true`，按当前锁定档位（没人选就用默认档 3）直接进 `playing`，同屏轮流走子。
- 理由：这是 H-6 与 v1 附录 A.3 承诺的延续 —— **用户不搭服务端节点图时，联机入口不能变成死路**。在待机室里卡住 15 秒后给一句 `没等到另一位玩家，也可以直接开始`，玩家有明确的下一步。
- **底部行恒定一句**：`FOOTER` 槽常显 `双方都点准备后开始`（`LOBBY_HINT`），**不随状态切换** —— 对手进出的瞬间底部行跳动会让玩家以为界面出故障。
- **单人提示只在提示条出一次**：`LOBBY_NOBODY`（`没等到另一位玩家，也可以直接开始`）写在 `HINT` 槽，满 15 秒仍未收到对方信号才出现，收到信号即清掉。玩家行同时仍显示 `对手　等待对手加入…`（那是「事实」，提示条是「下一步怎么办」，两件事分两个控件说）。

### 5.9 退出待机室

- `HINT` 行右端一个文字按钮 `返回主菜单`（无底框，只有字）。
- 点击：广播 `EV_READY(就绪=0)` 让对手知道我不在了，清房间状态，`T-10` 回 `start`。**不弹确认**（待机室没有对局可丢）。

## 七、悔棋交互规格

### 7.1 成对悔棋的精确语义

**定义**：一次悔棋 = **撤回最近 2 个半步（plies）**，即从 `P(n)` 回到 `P(n-2)`。

一次合法的悔棋之后：

| 量 | 变化 |
|---|---|
| 历史长度 | `n → n-2` |
| 轮到谁 | **不变**（`n` 与 `n-2` 奇偶相同 → 轮走方相同） |
| 白方损失 | 恰好 1 步（第 `n-1` 步） |
| 黑方损失 | 恰好 1 步（第 `n` 步） |
| 双方棋钟 | 回到 `history[n-2+1].clockW / clockB`（快照值） |
| 失子记录 | 回到该快照的 `capW / capB` 对应的列表前缀 |
| 走子记录 | 截断到 `n-2` 条 |
| 发起方悔棋计数 | `-1` |
| 对方悔棋计数 | 不变 |

**推演表（白方视角）**

| 历史 | 现在轮到 | 发起方 | 撤回后局面 | 撤回后轮到 | 白剩 | 黑剩 |
|---|---|---|---|---|---|---|
| 白1 黑1 | 白 | 白 | `P0` 开局 | 白 | 2 | 3 |
| 白1 黑1 白2 | 黑 | 黑 | `P1` | 黑 | 3 | 2 |
| 白1 黑1 白2 黑2 | 白 | 白 | `P2` | 白 | 2 | 3 |
| 白1（只 1 步） | 黑 | — | **不可悔**（`n < 2`） | — | — | — |

> **关键校验**：上表第 2 行 —— 黑方发起（黑刚走完白1黑1白2 → 轮到黑），撤回的是白2 和 黑1。也就是说黑方自己刚走的那一步（`黑1`）**也被撤掉了**，白方刚走的 `白2` 也撤掉了。这正是「双方各退一步」。撤回后轮到黑 —— 和撤回前一样。**没有信息泄露**：撤回的 2 手都是双方已经看过的。

### 7.2 发起条件（六条全满足才可点）

| # | 条件 | 不满足时 |
|---|---|---|
| C-1 | `GAME.screen == "playing"` | 按钮不可见/置灰 |
| C-2 | `not GAME.over` | 灰 + `棋局已结束，不能悔棋` |
| C-3 | `#GAME.history >= 3`（即 `n >= 2`，含开局快照） | 灰 + `开局还没走子，不能悔棋` |
| C-4 | **轮到本端**（联机：`GAME.mySide` 那一方；同屏：恒真，因为「本端」= 轮走方） | 灰 + `等轮到你时再悔棋` |
| C-5 | 本端剩余次数 > 0 | 灰 + `悔棋次数用完了`（文案见 7.3） |
| C-6 | `GAME.pendingPromo == nil`（升变弹窗未开） | 灰（升变不可撤） |

> **D-1 的落地就是 C-4**：「本方刚走完、轮到对方」时 C-4 不满足，按钮灰。玩家要悔自己那一步，必须等对方走一步 —— 这正好凑成「成对」。

### 7.3 次数与显示

- `CONFIG.UNDO_PER_SIDE = 3`。每局开始、`再来一局`、`新开一局`、`从此局面开新局` 时**双方都重置为 3**。
- 按钮文案：**`悔棋（剩 {n}）`** —— 括号用**全角** `（）`，但 `{n}` 里的数字用**半角**阿拉伯数字。
  例：`悔棋（剩 3）` / `悔棋（剩 0）`。
- `n` 的口径：**发起方视角的余额**。
  - 同屏：`n` = 当前轮走方的余额（因为发起方恒为轮走方）。
  - 联机：`n` = 本端玩家的余额（我执白就是白方余额；对方用掉他的次数不影响我的显示）。
- `n == 0` 时按钮文字仍为 `悔棋（剩 0）`，样式转置灰（底 `BTN_DIS_BG`、字 `BTN_DIS_TEXT`），命中区**可以保留**（点下去弹提示条），也可以 `SetActive(false)`。
  **规定：保留命中区 + 弹提示条**。理由：`SetActive(false)` 会让玩家以为按钮消失了，不知道为什么；弹一句 `悔棋次数用完了` 才是可理解的反馈。

### 7.4 单人 / 双人同屏流程

```
点「悔棋（剩 N）」
   ├ 条件不满足 → 提示条一句话，什么都没发生
   └ 满足 → 弹确认框
            正文：悔棋：双方各退一步
            按钮：确认悔棋 / 取消
              ├ 取消 → 关闭，局面不变，次数不变
              └ 确认 → 执行成对撤回（7.1）→ 次数 -1 → 提示条「已悔棋：双方各退一步」
```

- 同屏模式下**不需要对方同意**（同一个人操作两个颜色，没有「对方」这个实体）。
- 确认框是必需的：悔棋不可逆（次数一旦扣掉不返还），一步误触就白扔一次机会。

### 7.5 联机请求-同意-拒绝流程

```
我（轮走方）点「悔棋（剩 N）」
  → 弹确认框「悔棋：双方各退一步」→ 点「确认悔棋」
      → ① 本地进入「等待态」：冻结双方棋钟，pendingUndo = { byMe = true, t = 0 }
        ② 广播 EV_UNDO_REQ(a=我的身份, b=2)
        ③ 按钮文案改「等待对方同意悔棋…」，按钮与其余操作全部不可点
        ④ 提示条：已发出悔棋请求，等待对方同意

对方收到 EV_UNDO_REQ（非回声）
  → 弹确认框「对方请求悔棋，同意吗」→ 同意悔棋 / 拒绝悔棋
      ├ 同意 → 广播 EV_UNDO_ACC(a=对方身份) → 本地立即执行成对撤回
      │        → 发起方收到 EV_UNDO_ACC → 执行成对撤回（自己一侧）
      └ 拒绝 → 广播 EV_UNDO_NO(a=对方身份)

发起方收到 EV_UNDO_NO   → ① 解冻棋钟 ② 提示条「对方拒绝了悔棋」③ 次数不扣（未发生）
发起方 15 秒未收到任何回应 → 视同拒绝：解冻 + 提示条「对方没有回应，悔棋已取消」，次数不扣
```

- **次数何时扣**：**只有真正执行了撤回才扣**。请求被拒 / 超时 / 对端掉线，一律不扣。
- **棋钟冻结窗口**：从「发出请求」到「收到 ACC/NO/超时」。这期间 `OnUpdate` 不累加、不扣时、不判超时。
- **响应方是否也冻结**：是。响应方在弹框期间同样冻结 —— 它没法走子（轮走方不是他），冻结只是防「发起方等他的 15 秒里发起方的钟白烧」。
- **重复请求**：`pendingUndo ~= nil` 时再点无效（弹 `已有一个悔棋请求在等待回应`）。
- **执行时机必须两端一致**：`EV_UNDO_ACC` 是「执行」信号，双方都在收到/发出它的那一帧执行。发起方不能「点了确认就本地先撤回」—— 那会在对方拒绝时出现只有一方撤回的**分叉**（比 v1.4 的 D-05 回声 bug 更严重）。

### 7.6 棋钟与快照回退（实现要点，最容易做错的地方）

撤回后必须**一整组**状态同时回退，漏任何一个都是隐性错误：

| # | 状态 | 回退方式 | 漏了会怎样 |
|---|---|---|---|
| 1 | `GAME.st` | `RULES.parse_fen(GAME.history[n-1].fen)` 重建 | 局面没退 |
| 2 | `GAME.st.history`（三次重复用的 position_key 序列） | **必须回填**：对保留下来的每个快照 `RULES.position_key(RULES.parse_fen(snap.fen))` 依次填入 | `parse_fen` 会把 `st.history` 清空 → **本局再也判不出三次重复**（静默失效） |
| 3 | `GAME.clockWhite / clockBlack` | `history[n-1].clockW / clockB` | 时间不退 |
| 4 | `GAME.moveLog` | 截断到 `n-2` 条 | 记录不退 |
| 5 | `GAME.capturedWhite / capturedBlack` | 重建到该快照的 `capW / capB` | 失子不退 |
| 6 | `GAME.history` | 截断到 `n-1` 项（第 0 步快照保留） | 复盘还能翻到已撤的步 |
| 7 | `GAME.lastFrom / lastTo`（上一步痕迹） | `history[n-1].from / to` | 痕迹指向已撤的格 |
| 8 | **`GAME.lastSentMove`** | **置 `nil`** | 回声过滤会误吞对方的下一步走子（`lastSentMove` 匹配的是已撤掉的那一手） |
| 9 | `GAME.selected / legalTargets / legalMoves` + 高亮 | `clear_highlights()` | 高亮残留在已撤的格上 |
| 10 | `GAME.elapsedSec` | 按快照时间回溯（用两快照差值减） | 结算说明行的「本局用时」偏大 |

- **不做反向动画**：直接重绘终态。
- **不重算 `GAME.st.halfmove`**：`parse_fen` 从 FEN 里读，正确。

## 九之二、平台约束：文本框板高 ≥ 2.1 × 字号（**单独立节，因为已经害了三次**）

### 9.7.1 规则

> **任何承载文字的文本框控件，其板高必须 ≥ 2.1 × 字号。**
> 推导：行高 ≈ 1.2 × 字号，上下内边距合计 ≈ 0.9 × 字号，**1.2 + 0.9 = 2.1**。
>
> 等价写法：`字号 ≤ 板高 / 2.1`；`板高比例 h ≥ 字号 × 2.1 / 900`（1600×900 基准）。

**违反的后果不是截断，而是整行被吞掉 —— 什么都不显示，也不报错。**
这是本项目最贵的一条约束：它不产生任何日志、不留任何痕迹，只能靠人眼看截图才发现。

### 9.7.2 为什么是 2.1 而不是别的数（用本项目的实测证据校准）

| 证据 | 板高 / 字号 | 结果 |
|---|---|---|
| v1.4 结算面板标题，`h=18%`（64.8px）/ 字号 44 | **1.473** | **整行消失**（实测，缺陷 D-02） |
| v1.4 修后，`h=26%`（93.6px）/ 字号 44 | **2.127** | 正常显示（实测） |
| `tech-architecture.md` 早期写的「44 号至少要 72px」 | 1.636 | **落在未验证区间，是错的判据** |

- 2.1 规则对成功点 `93.6 ≥ 92.4` 判 PASS、对失败点 `64.8 < 92.4` 判 FAIL，**两侧都吻合实测**。
- 早期那条「44 号至少 72px」落在 1.473 与 2.127 之间，用它当闸门会放行 72~92px 这一段
  —— 那一段**从未被验证过**，正是最容易出事的灰区。

### 9.7.3 已经踩过三次

| # | 版本 | 现象 | 根因 |
|---|---|---|---|
| 1 | v1.10 | 结算面板标题整行不显示 | `h=18%`（64.8px）装 44 号字，比值 1.473 |
| 2 | v2.0 块 1 | 档位名整行消失（Lead 截图确认） | 卡高 0.190×900=171px 只分给档位名 41px，字号 28 需 58.8px，比值 1.46 |
| 3 | v2.0 块 2 | 倒数数字 | 板高 103.5px 曾配字号 72，比值 **1.437**（后定为 48，比值 2.156 ✅） |

三次的比值都在 **1.44 ~ 1.47**，非常接近 —— 这解释了为什么它总以「差不多快够」的样子骗过人眼。
